If you know [XState](https://stately.ai/docs/xstate), most concepts carry over — the spelling
and the mechanics change. This page maps them, then explains where the two libraries differ
in spirit. It's a conceptual guide, not a benchmark.

## Concept mapping

| XState | effstate v4 |
|---|---|
| `createMachine(config)` | `defineMachine(config)` |
| String state values (`"running"`) | `State("Running", { ... })` variants — a discriminated union whose data lives on the state |
| `context` + `assign(...)` | A plain context object patched via `{ update: { ... } }` from a handler |
| Guards (`guard`, `and`, `or`, `not`) | Plain conditionals in the handler — return the transition when it holds, else `null` |
| `actions` | `{ actions: [() => {...}] }` for fire-and-forget sync work, or `{ update }` to change context |
| `activities` and `invoke` | `run` streams — emit events while in the state, auto-cancelled on exit |
| Injected services / actor logic | Effect requirements (`R`) provided via layers, consumed in `entry`/`run` |
| `interpret(machine)` / `createActor` | `machine.interpret()` — a method returning an `Effect` |
| `sendTo` / `sendParent` | `useActorBridge` — React owns actor refs and wires them together |

### States hold their own data

In XState a state is a string and everything variable lives in `context`. In effstate a
state is a tagged variant that can carry data intrinsic to it:

```ts
const Running = State("Running", { startedAt: Schema.DateFromSelf });
// ...
Start: () => ({ goto: Running.make({ startedAt: new Date() }) }),
```

Data that isn't part of the state's identity (the elapsed count) stays in context.

### assign becomes update

```ts
// XState: actions: assign({ elapsed: ({ context }) => context.elapsed + 1 })
Tick: (ctx) => ({ update: { elapsed: ctx.elapsed + 1 } }),
```

`update` is a shallow `Partial<C>` merge — no `assign`, no updater objects.

### Guards become conditionals

There is no separate guard function or `and`/`or`/`not` combinators. A handler is just a
function; return `null` to stay put.

```ts
Tick: (ctx) =>
  ctx.elapsed < 60 ? { update: { elapsed: ctx.elapsed + 1 } } : null,
```

### Activities and invoke become run streams

A `run` stream replaces both long-running activities and invoked sources. It's a typed
`Stream` of events that starts on entry and is interrupted on exit:

```ts
Running: {
  run: ticks, // Stream<StopwatchEvent> — emits Tick every second
  on: { Tick: (ctx) => ({ update: { elapsed: ctx.elapsed + 1 } }) },
},
```

### Services become Effect requirements

Instead of injecting actor logic, entry effects and run streams are ordinary `Effect`s whose
requirement channel (`R`) is satisfied with a layer at interpret time:

```ts
Effect.runSync(machine.interpret().pipe(Effect.provide(MyServiceLayer)));
```

### Cross-actor communication is a React concern

There's no `sendTo`/`sendParent` inside the machine. In React, `useActorBridge` watches one
actor and forwards derived values as events to another:

```tsx
useActorBridge(
  source.actor, target.actor,
  (snap) => snap.context.electricityLevel > 0,
  (isPowered) => (isPowered ? PowerOn.make() : PowerOff.make()),
);
```

## What's different in spirit

- **Schema-first.** One `State`/`Event` definition is simultaneously the type, the
  constructor, the guard (`.is`), and the codec (`.schema`). There's no separate typegen step.
- **Effect-native effects.** Side effects aren't strings resolved against an implementation
  map — they're `Effect`s and `Stream`s with real requirements and error channels. Failures
  surface through `onError` as structured `MachineEffectError`s rather than being swallowed.
- **A lean, imperative actor.** The actor is a small object with `send`, `getSnapshot`,
  `subscribe`, and `stop`. No always-on inspector, no observable protocol — the whole core is
  roughly ~500 LOC.

<Aside type="tip">
Migrating incrementally? Start by translating one XState machine's states into `State(...)`
variants, move `context` fields over, and rewrite `assign` calls as `{ update }`. Guards and
actions fall out naturally once the handlers are plain functions.
</Aside>
